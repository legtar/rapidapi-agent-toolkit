# PROVIDER_GUIDE — как стать провайдером на RapidAPI (и Этап 2: свой YouTube-API)

Две части: (1) общий процесс публикации своего API на RapidAPI; (2) конкретный план Этапа 2 —
обернуть свой парсер поиска YouTube в API и протестировать локально.

---

## Часть 1. Как устроен провайдинг на RapidAPI

RapidAPI = маркетплейс-**прокси**. Он НЕ хостит твой код — он стоит шлюзом перед твоим
публичным HTTP-API, считает вызовы, берёт оплату, отдаёт тебе выручку.

Схема запроса:

```
Потребитель → RapidAPI прокси (<host>.p.rapidapi.com) → ТВОЙ бэкенд (публичный URL)
              добавляет X-RapidAPI-Proxy-Secret ↑        проверяет этот секрет
```

### Шаги публикации

1. **Свой рабочий HTTP-API.** Обернуть парсер в веб-сервис (FastAPI/Flask), задеплоить на публичный
   URL (VPS/облако/сервер). RapidAPI дёргает именно его.
2. **Provider Dashboard → Add New API.** Указать базовый URL, добавить эндпоинты.
   Удобнее всего — импортом **OpenAPI (Swagger)** спецификации.
3. **Proxy-secret.** RapidAPI шлёт на твой бэкенд заголовок `X-RapidAPI-Proxy-Secret`.
   Твой сервис обязан пропускать только запросы с верным секретом — иначе API дёргают в обход,
   мимо биллинга.
4. **Тарифы (Plans).** Basic/Pro/Ultra/Mega + квоты (rate limit, лимит вызовов/мес) + цены.
   Часто Basic делают бесплатным (freemium) для привлечения.
5. **Публикация и модерация.** После проверки API появляется в каталоге и в поиске (`searchApis`).
6. **Деньги.** RapidAPI берёт комиссию (~20%), выплаты через Stripe/PayPal.

### ⚠️ Юридический риск именно для YouTube-парсера

- Скрапинг YouTube нарушает **YouTube Terms of Service** (официально данные отдаёт только YouTube Data API).
- Google рассылает жалобы/DMCA — RapidAPI **снимает** такие API с публикации (на маркетплейсе видно
  «кладбище» умерших YouTube-скраперов).
- Ответственность за нарушение ToS/копирайта/персональных данных по provider-agreement лежит на **тебе**,
  не на RapidAPI.
- Практика: подобные API существуют и зарабатывают, но живут «до первой жалобы». Планируй запасной
  хостинг/аккаунт и не завязывай на них критичный доход.

## Часть 2. Этап 2 (план) — обернуть свой парсер поиска YouTube в API

Статус: **план, реализуем позже**, когда подставишь свой парсер. Здесь — целевая структура и как
протестировать **локально** (без RapidAPI).

### Целевая структура

```
provider/
  app.py            # FastAPI: эндпоинты + проверка X-RapidAPI-Proxy-Secret
  youtube.py        # def youtube_search(query, limit) -> list[dict]   <- сюда твой парсер
  openapi.yaml      # спека для импорта в Provider Dashboard
  requirements.txt  # fastapi, uvicorn, (+ то, что нужно парсеру)
```

### Черновой контракт API

```
GET /search?q=<строка>&limit=<N>
Заголовок: X-RapidAPI-Proxy-Secret: <секрет>   (в реальном вызове его подставляет RapidAPI)

200 → {
  "query": "...",
  "count": N,
  "results": [
    {"video_id": "...", "title": "...", "channel": "...", "url": "...",
     "views": 12345, "published": "...", "duration": "..."}
  ]
}
```

`youtube_search()` — единственное место с твоей логикой; каркас от неё не зависит.

### Как тестировать локально (Этап 2, без RapidAPI)

1. `uvicorn provider.app:app --port 8000`
2. Проверить эндпоинт и защиту proxy-secret:
   ```powershell
   # без секрета -> 401
   curl "http://localhost:8000/search?q=lofi&limit=5"
   # с секретом -> 200 + JSON видео
   curl "http://localhost:8000/search?q=lofi&limit=5" -H "X-RapidAPI-Proxy-Secret: dev-secret"
   ```
3. Убедиться, что структура ответа совпадает с `openapi.yaml`.

Полный круг через RapidAPI (публичный URL/туннель → Add New API → Subscribe → вызов через
`*.p.rapidapi.com`) — отдельный шаг после того, как локальный тест зелёный. По решению — пока только локально.

### Что нужно от тебя, чтобы реализовать Этап 2

- Код/функция твоего парсера поиска YouTube (что на входе, что на выходе), либо разрешение
  использовать встроенную реализацию (innertube/yt-dlp) как временную.
